歷史文件，不代表成品規格。

`捕手偷好球專案企劃書.md` 是動工前寫的研究計畫，內容是「預計要做什麼」。
成品在若干地方與它不同，以 repo 根目錄的 README 為準：

| 項目 | 企劃書（計畫） | 成品（實際） |
|---|---|---|
| 球季範圍 | 2021–2025 | 2021–2023 |
| 樣本 | 約 175 萬球 | 106 萬顆判定球（建模 104 萬） |
| 階層模型引擎 | R `glmmTMB` 或 PyMC | Python statsmodels 變分貝葉斯 |
| XGBoost 黑箱對照 | 列為主力對照 | 未做 |
| 主審資料來源 | 未指定 | MLB Stats API（以 `game_pk` join） |

企劃書第 8 節把 2026 年 ABS 制度形容為「一項技術的死亡」。ABS 挑戰制度自 2026 年
球季起在大聯盟例行賽實施，但它是「挑戰制」而非全自動判定，較準確的說法是
framing 的衡量方式與價值可能因此改變，而非消失。

## v2（2026 年 9 月）

[`PLAN.md`](PLAN.md) 是第二輪動工前寫的工作計畫，內容是「預計要做什麼」。它原樣
保留，未經事後修改——包括後來被實測推翻的部分。下表把它預計做的事和實際做出來的
事並列，格式與上表相同。結論以 repo 根目錄的 [`README.md`](../README.md) 與
[`METHODS.md`](../METHODS.md) 為準。

計畫文首提到的 `NOTES.md`（工作日誌）與 `README-v1.md` 最後都沒有進版控，所以
計畫裡指向它們的段落在 repo 裡找不到對應檔案。v1 的舊版改由 `v1.0` tag 提供。

| 項目 | 計畫 | 實際 |
|---|---|---|
| 換推論引擎的理由 | VB 沒收斂、後驗變異數偏小，區間不可用 | VB 與 NUTS 的捕手效果相關 0.9999、sd 只低估 5%；理由改成「Step 5、6 需要後驗樣本」 |
| shadow zone 的理由 | MCMC 跑得動的前提 | 全量也跑得動（單季約一小時）；理由改成資訊量（14.5% 的球帶 60.8% Fisher information）與能便宜地反覆擬合 |
| 模擬情境數 | 4 個，外加 1 個「模型設錯」 | 8 個。設錯那格拆成四個版本，其中三個設計失敗（模型把要打壞它的東西吸收掉了） |
| 設錯情境的預期 | 會打壞階層模型的 coverage | 三個都沒打壞，八情境全在 92.9–95.6%。改以「混淆要多大才會壞」的強度掃描回答 |
| 球季切分 | Train 2021–2023 / Val 2024 / Test 2025 | 2021–2022 train、2023 holdout；2024–2025 未抓 |
| Step 2 的曲面重構、Step 3 的增量表 | optional，校準問題浮現後一度想提上主線 | 維持 optional，未做——S 形校準偏差對榜單全距的影響只有 1% |
| 工作日誌 NOTES.md | 整理成 METHODS.md 的來源，會進 repo | 保持私人；METHODS.md 另外寫成可獨立閱讀的技術文件 |
| v1 的 README | 以 `README-v1.md` 留在 repo，新 README 連過去 | 未進版控；改由 `v1.0` tag 提供舊版 |

計畫開頭列了四條 v1 的問題，並把「階層模型用變分貝葉斯擬合且未收斂」排在第一位，
當成開工的理由。跑完之後那是四條裡唯一沒有後果的一條。真正有後果的是第二條和
第三條——全專案沒有區間、沒有任何數字被已知真值檢驗過——而它們在計畫裡的位置
比較後面。這件事寫進了 README 的 What I'd do differently。
